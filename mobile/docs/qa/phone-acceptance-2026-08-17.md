## QA-1 — надиктовка темы распознаёт русскую речь как латиницу

**Серьёзность:** баг (не блокер — тема набирается с клавиатуры)

**Экран:** «New collection» → поле DESCRIBE THE SITUATION → кнопка микрофона

**Шаги репро**

1. Язык интерфейса приложения — английский (следует языку системы).
2. Открыть создание коллекции, переключить клавиатуру на русскую.
3. Нажать микрофон и продиктовать тему по-русски.

**Ожидалось:** в поле появляется продиктованный русский текст.

**Вышло:** в поле легла латиница, не имеющая отношения к сказанному —
`Pako Ka Ko Ma Saba Majiya`. Русская речь прогоняется через англоязычный распознаватель
и транслитерируется в случайные слоги.

**Диагноз (гипотеза).** `mobile/lib/features/collections/generate_screen.dart:177` передаёт
`localeId: _sttLocales[uiCode] ?? 'en_US'`, где `uiCode` берётся из
`Localizations.localeOf(context).languageCode` (строка 124) — то есть из локали **интерфейса**.
При английском UI распознаватель всегда стартует в `en_US`, независимо от языка клавиатуры и от
того, на каком языке человек говорит. Карта `_sttLocales` (строки 107–111) содержит `ru_RU`, но
до неё дело не доходит. Правильный сигнал — язык-источник коллекции (`source_lang`, у владельца
`ru`) либо язык активной клавиатуры, а не локаль UI.

**Выписка из БД/лога:** записи нет — генерация не запускалась, обращений к API не было.

## QA-3 — сгенерированная коллекция висит в списке дважды до перезапуска приложения

**Серьёзность:** баг

**Экран:** «Collections» → сегмент «Mine»

**Шаги репро**

1. Создать коллекцию через генерацию, дождаться готовности не выходя из приложения.
2. Посмотреть список «Mine».

**Ожидалось:** одна строка — готовая коллекция.

**Вышло:** две строки одной и той же коллекции: сверху карточка генерации со значком
«Ready» и обрезанным заголовком, под ней настоящая строка коллекции
(«10 words · 0 mastered», «Triage 10»). Владелец сообщает, что это уже не первый прогон
с таким поведением. Обычное обновление экрана дубль не убирает.

**Диагноз (гипотеза).** `mobile/lib/features/collections/collections_screen.dart:129-144`
рисует подряд **все** строки `pendingGenerationsProvider`, а следом **все** строки
`collectionsProvider`, без фильтра «не показывать pending, чья коллекция уже приехала».
В `mobile/lib/data/generation_controller.dart:197-206` успешная генерация не удаляет
pending-строку, а лишь помечает её `status='succeeded'` и проставляет `collectionId`.
Удаление такой строки живёт только в `reconcile()` (там же, строки 114-118), который
выполняется **на старте приложения**. Отсюда и симптом: в текущей сессии дубль не уходит
ни сам, ни по pull-to-refresh (`resync()` трогает только зеркало коллекций), а исчезает
после перезапуска. Минимальная правка — либо удалять pending сразу после успешного `_sync()`,
либо отфильтровывать в списке те pending, чей `collectionId` уже есть среди коллекций.

## QA-4 — обложка коллекции не приезжает: серый плейсхолдер до следующего синка

**Серьёзность:** баг (самовосстанавливается при следующем синке)

**Экран:** «Collections» → сегмент «Mine»

**Шаги репро**

1. Сгенерировать коллекцию, дождаться готовности.
2. Смотреть строку коллекции сразу после появления.

**Ожидалось:** обложка коллекции.

**Вышло:** серый квадрат-плейсхолдер у обеих строк. Картинка появляется только после
повторного обновления экрана.

**Выписка из БД и API-лога.** Обложка на сервере есть и валидная:

```
01M08AP71D1KM0PFPYK3P71DV5 | Buying Dog Food at the Store
image_url    = https://images.pexels.com/photos/10330689/... (Pexels, автор David Henry)
```

Хронология из `api_request_logs` объясняет гонку:

```
17:00:44  POST /v1/chat/completions   purpose=generation   → коллекция создана
17:00:45  GET  api/v1/sync            ← клиент синкается ЗДЕСЬ
17:00:46  GET  /v1/search             purpose=images   ┐
...       ещё 11 запросов картинок               │ обложки приезжают ПОСЛЕ синка
17:00:53  GET  /v1/search             purpose=images   ┘
```

**Диагноз (гипотеза).** `mobile/lib/data/generation_controller.dart:205` вызывает `_sync()`
ровно один раз — сразу по `succeeded`. Комментарий рядом обещает «and their images as they
land», но повторного синка нет, а поиск обложек на сервере идёт **после** ответа генерации
(12 вызовов `/v1/search` в течение 8 секунд). Клиент забирает снимок, где `image_url` ещё
пустой, и держит его до следующего синка. Предложение владельца — тянуть картинки
параллельным запросом — бьётся с этой же картиной: либо сервер отдаёт генерацию готовой
вместе с обложкой, либо клиент повторяет синк после того, как картинки осели.

## QA-5 — админка не показывает слова, размеченные «не знаю»: телефон и админка расходятся

**Серьёзность:** баг

**Экран:** админка → «Прогресс обучения» (список пар и корзина «НОВЫЕ»)

**Шаги репро**

1. Разметить триажем коллекцию, поставив части слов «не знаю».
2. Открыть «Прогресс обучения» по этому пользователю.

**Ожидалось:** либо размеченные «не знаю» слова видны, либо текст не обещает, что они появятся.

**Вышло:** пустое состояние гласит «Слово попадает сюда после первой встречи — интро, ответа
или триажа», но триаж с вердиктом «не знаю» строку не создаёт. После разметки 10 слов
(6 «не знаю», 2 «не уверен», 2 «знаю») список показывает `ВСЕ 4`, а `НОВЫЕ 0` — шести
размеченных слов на экране нет вовсе.

**Выписка из БД**

```
term_triages          — 10 строк (6 unknown, 2 unsure, 2 known), client_seq 521…530
user_term_progress    —  4 строки: 2 learning/step 1, 2 graduated/known
```

**Диагноз (для QA-5).** Поведение данных верное и намеренное — в докблоке
`backend2/app/Modules/Learning/Application/Command/TriageTermsHandler.php:38` прямо записано
«unknown → leave it new», строка прогресса не создаётся. Расходится **текст** пустого
состояния: он перечисляет триаж среди событий, создающих строку, что справедливо лишь для
вердиктов «знаю» и «не уверен». Отличать от известной особенности 8 (там речь о словах, с
которыми встречи ещё **не было**) — здесь встреча была.

**Почему это баг, а не семантика.** Две поверхности над одним состоянием говорят разное:
телефон показывает `Learn 6` и закрашенную первую точку у всех шести, админка — `ВСЕ 4`
и `НОВЫЕ 0`. Корзина «НОВЫЕ» при этом структурно недостижима из триажа: наполниться она
может только после интро. Чинить следует **сторону чтения**, а не запись — создавать строки
`new`/step 0 нельзя, это сломает признак «слово новое ⇔ у него нет non-new строки прогресса»
(`TriageTermsHandler.php:35`). Проекция `Admin` вправе доставать термины, у которых есть
триаж без пары, и показывать их синтетической ступенью 0 — модуль и задуман как
reporting projection над чужими данными, собственных таблиц он не заводит.

## QA-6 — на узнавании варианты разной формы: слово против предложений, ответ угадывается по длине

**Серьёзность:** баг

**Экран:** учебная сессия → карточка узнавания (ступень 1), кадр «Getting to know»

**Шаги репро**

1. Коллекция из смеси слов и предложений (здесь: 4 предложения + 2 слова в сессии).
2. Начать сессию, дождаться карточки узнавания для **слова**.

**Ожидалось:** четыре сопоставимых по форме варианта — карточка проверяет знание слова.

**Вышло:** для слова `grain-free` предложены `без злаков` (верный), `сухой корм`,
`Где я могу найти корм для собак?`, `Подходит ли это для мелких пород?`. Два варианта —
целые вопросительные предложения, очевидно не могущие быть переводом одного слова.
Отбросив их по форме, не зная слова, учащийся получает выбор из двух: 50 % вместо 25 %.

**Диагноз (гипотеза).** Ровно то, против чего написан собственный докблок ассемблера
`backend2/app/Modules/Learning/Application/Service/StudyCardAssembler.php:33-37`:
«Far options make the card answerable by knowing the word and by nothing else». На ступенях
1–2 дистракторы намеренно берутся не из `example_distractors`, а из **соседей по колоде**
(там же, строки 232-273) — и никакого условия «сосед той же формы» в отборе нет. В колоде
6 фраз/идиом на 4 слова, поэтому вариантами к слову регулярно встают целые предложения.
Форма варианта становится подсказкой, и цель докблока не достигается.

Второй, более грубый случай в том же прогоне — узнавание-2 (перевод → термин): на запрос
«без злаков» даны `Would you like a receipt?`, `do you have any discounts?`,
`How much does this bag cost?` и `grain-free`. Верный вариант единственный короткий —
ответ виден, даже не читая. Направление правки: при наборе пула предпочитать соседей с
тем же `type`, а при нехватке — уменьшать число вариантов, а не добивать разнородными.

## QA-7 — у части фраз «пример» дословно повторяет сам термин

**Серьёзность:** баг

**Экран:** карточка интро (кадр 16b); тот же пример уходит и в карточку слова 16e

**Шаги репро**

1. Сгенерировать коллекцию, где среди терминов есть фразы-предложения.
2. Дойти в сессии до интро такой фразы.

**Ожидалось:** пример — предложение, показывающее термин в контексте.

**Вышло:** на интро `Where can I find dog food?` строка примера — ровно тот же текст,
`Where can I find dog food?`. Карточка показывает одно и то же дважды, контекста нет.

**Выписка из БД.** Дефект есть у 3 из 10 терминов коллекции — сравнение
`lower(btrim(terms.text)) = lower(btrim(term_examples.sentence))`:

```
Where can I find dog food?          | phrase | Where can I find dog food?                   | СОВПАДАЕТ
Is this suitable for small breeds?  | phrase | Is this suitable for small breeds?           | СОВПАДАЕТ
How much does this bag cost?        | phrase | How much does this bag cost?                 | СОВПАДАЕТ
do you have any discounts?          | phrase | Do you have any discounts on dog food?       | ок
Would you like a receipt?           | phrase | Would you like a receipt with your purchase? | ок
tailor to their needs               | idiom  | Choose dog food that is tailored to their…   | ок
grain-free / organic / canned food / dry kibble | word | нормальные контекстные примеры    | ок
```

**Диагноз (гипотеза).** Не системное свойство фраз, а непостоянство генерации: две другие
фразы и идиома получили развёрнутые примеры, а три — эхо самих себя. На приёмке ответа
генерации нет проверки «пример ≠ термин». Дешёвая правка — отбраковывать такой пример при
валидации ответа модели и просить перегенерацию примера (механизм `example_regenerations`
уже есть). Смежно, но отдельно от известной особенности 3 (полужирный термин внутри примера
не срабатывает для фраз с пунктуацией): здесь совпадает весь текст целиком.

## QA-8 — на промахе баннер обещает «верную форму ниже», а ниже стоит сам термин

**Серьёзность:** мелочь (текст)

**Экран:** учебная сессия → узнавание (ступень 1) → состояние после неверного ответа

**Шаги репро**

1. На карточке узнавания-1 (запрос английским термином, варианты русские) выбрать неверный вариант.
2. Прочитать баннер вердикта и то, что под ним.

**Ожидалось:** текст указывает туда, где действительно лежит верный ответ.

**Вышло:** баннер `Not quite — the correct form is below`, при том что верный вариант
(`Где я могу найти корм для собак?`) отмечен зелёной галочкой **выше**, в списке вариантов.
Ниже же расположена карточка-напоминание с самим термином `Where can I find dog food?` —
картинка, транскрипция, пример. Это не «верная форма», а повторный показ спрошенного.

**Диагноз (гипотеза).** Формулировка общая для режимов, где ответ вводится или собирается

ответ уже подсвечен в списке, а снизу идёт ре-тич термина, поэтому текст отсылает не туда.
Просится отдельная строка вердикта для режимов узнавания.

**Не путать** с известной особенностью 6 (в разборе итога у карточек ступени 1 заголовок и
подпись — один и тот же термин): здесь речь о баннере внутри самой сессии.

## QA-9 — после промаха слову выдаётся карточка ступени, на которой оно не стоит

**Серьёзность:** баг (счёт ступеней при этом корректен — цена промаха ровно одна ступень)

**Экран:** учебная сессия, карточки узнавания

**Шаги репро**

1. Слово приходит в сессию новым: интро → узнавание-1 → узнавание-2.
2. На узнавании-1 ответить **неверно**.
3. Доиграть до узнавания-2 того же слова и ответить **верно**.

**Ожидалось:** проваленная ступень переигрывается — слово возвращается тем же
узнаванием-1, пока не будет пройдено.

**Вышло:** слово вернулось карточкой 11 из 16 сразу **узнаванием-2** (русский запрос,
английские варианты), хотя пара после промаха стояла на ступени 1. Верный ответ записан
как ответ на **ступень 2**, и пара поднялась 1 → 2.

Учёт ступеней при этом **не сломан**: каждый верный ответ поднимает пару ровно на одну
ступень, независимо от того, какой ступенью подписана карточка. Цена промаха — ровно одна
ступень, и она уплачена: из шести слов сессии пять дошли до `graduated` за два верных
ответа, а `Where can I find dog food?` закончило на ступени 2. Дефект не в счёте, а в том,
**какую карточку показали**: учащегося спросили обратным направлением (перевод → термин),
не дав ему пройти прямое, на котором он ошибся.

**Выписка из БД**

```
seq 1694 | Where can I find dog food? | ladder_step 1 | again | is_correct f | response 01M08AP74HM20AA0FDH2RSF5XS
         → пара осталась: learning, learning_step = 1
seq 1696 | Where can I find dog food? | ladder_step 2 | hard  | is_correct t | response "Where can I find dog food?"
         → пара стала:   learning, learning_step = 2
```

**Диагноз.** Не гонка и не клиент — так устроена сборка сессии.
`backend2/app/Modules/Learning/Application/Command/BuildStudySessionHandler.php:36` персистит
сессию с **фиксированным** порядком, а `arrange()` (там же, строки 183-207) раскладывает на
каждый термин сразу всю **цепочку** карточек — интро и два узнавания — исходя из ступени,
прочитанной **один раз, на старте сессии**. После ответа план не пересобирается, поэтому
карточка узнавания-2 раздаётся независимо от того, чем кончилось узнавание-1.

Два следствия, второе тише и хуже:

1. Проваленная ступень не переигрывается: прямое узнавание, на котором учащийся ошибся,
   в этой сессии больше не показывается — вместо него идёт обратное.
2. В `reviews` остаётся строка `ladder_step = 2` для пары, которая в этот момент стояла на
   ступени 1. Любая аналитика по ступеням считает ответ данным на ступень, на которой
   учащегося не было. Это видно живьём: в ленте админки событие 11-минутной давности по
   `Where can I find dog food?` подписано «ст. 2 ✓верно», хотя пара стояла на ступени 1.

Направление правки: либо пересобирать хвост сессии после промаха, либо на выдаче карточки
сверять запланированную ступень с текущей ступенью пары и клампить — механизм клампа уже
есть (`LearningLadder::clampRecognitionStep`, обёртка `LadderStepResolver`), он просто не
применяется к раздаче карточек внутри уже собранной сессии.

**Экран:** итог сессии («Session complete») → плашка Daily goal

{"learned": 0, "mastered": 2, "new_goal": 20, "due_today": 0, "new_today": 4,
 "active_days": ["2026-08-17"], "streak_days": 1, "total_terms": 8,

дефект `statsProvider`. Симптом другой, поэтому записан отдельно; если после перезапуска
приложения плашка покажет `4 / 20`, оба следует чинить одной правкой.

## QA-11 — в дневной статистике «верно» считается иначе, чем в самом ответе: 4 из 12 вместо 11 из 12

**Серьёзность:** баг

**Экран:** невидим напрямую; проекция `daily_user_stats`, питающая статистику удержания

**Шаги репро**

1. Пройти сессию, отвечая верно, но не быстро (грейд `hard`).
2. Сравнить `reviews.is_correct` с `daily_user_stats.correct_count` за тот же день.

**Ожидалось:** одна и та же трактовка «верного ответа» в обоих местах.

**Вышло:** за день 12 ответов, из них по `is_correct` верных **11**, неверный **1**.
В `daily_user_stats.correct_count` записано **4**.

**Выписка из БД.** Грейды двенадцати ответов: `hard, good, hard, hard, again, hard, hard,
hard, hard, good, good, good` — ровно 4 штуки `good`, и столько же попало в `correct_count`.

```
reviews          | 12 всего | is_correct = t → 11 | is_correct = f → 1
daily_user_stats | reviews_count 12 | correct_count 4
```

**Диагноз.** `backend2/app/Modules/Learning/Domain/ValueObject/Grade.php:16` определяет
`isCorrect()` как `Good || Easy` — `Hard` считается неверным. Проектор
`EloquentDailyStatsProjector.php:61-63` инкрементирует `correct` именно по этому признаку,
а не по колонке `is_correct` самой строки ревью. В итоге у одного и того же события два
несовпадающих определения «верно» внутри одного модуля.

Возможно, это осознанный выбор («retention = вспомнил без запинки»), но практический эффект
на лестнице тяжёлый: на ступенях узнавания `hard` выставляется по задержке очень охотно —
в этом прогоне 7 ответов из 12 получили `hard` просто потому, что между тапами шёл разбор.
Точность за день выходит 33 % при фактических 92 %. Как минимум просится переименование
(`isConfidentRecall()`) и явное решение, что показывать пользователю.

## QA-13 — в подсказке pick_correct исправление приезжает вместе с вопросительным знаком

**Серьёзность:** мелочь

**Экран:** свободная практика → `pick_correct` → состояние после неверного ответа

**Шаги репро**

1. В практике выбрать неверное предложение (здесь `Is the dog food in organic?`).
2. Прочитать строку исправления под вариантом.

**Ожидалось:** `should be: organic`.

**Вышло:** `should be: organic?` — с вопросительным знаком, попавшим внутрь исправления.
Подставить это в предложение нельзя: получится `Is the dog food organic??`.

**Выписка из БД**

```
term organic · пример «Is the dog food organic?»
 in organic → correction «organic?»   error_type preposition
 organics   → correction «organic?»   error_type tense
```

**Диагноз (гипотеза).** Обогащение (`generator_version = enrich-v1`) режет `correction` по
границе предложения и захватывает финальную пунктуацию. Валидации «correction не содержит
знаков конца предложения» на приёмке ответа модели нет.

**Смежно:** у второго дистрактора `organics` (ошибка в форме слова, множественное число)
проставлен `error_type = tense`. В перечне типов
(`article, preposition, tense, word_order, false_friend, modal_to`) категории для
числа/словоформы просто нет, и модель берёт ближайшую. Пользователю тип не показывается,
но любая статистика по типам ошибок будет врать.

## QA-14 — «Train this word» даёт ровно одну карточку

**Серьёзность:** баг (расхождение обещания кнопки с поведением)

**Экран:** карточка слова 16e → «Train this word»

**Шаги репро**

1. Открыть карточку любого слова, доступного для практики.
2. Нажать «Train this word».

**Ожидалось (ожидание владельца):** слово прогоняется по разным режимам — тому самому
вееру, ради которого практика и существует.

**Вышло:** сессия `1 of 1`. Одна карточка, один режим, конец. Чтобы получить другой режим,
нужно выйти и зайти снова.

**Диагноз.** Так устроено намеренно, но обещание кнопки этому не соответствует.
`backend2/app/Modules/Learning/Application/Command/BuildStudySessionHandler.php:125-129`:
«Practice keeps its flat running order (**one card per term**, already shuffled)» — на один
термин выдаётся ровно один слот. Веер режимов из `ExerciseSelector::selectForPractice`
(`ExerciseSelector.php:146-173`) раскручивается по **индексу карточки**, поэтому «одна
сессия показывает все применимые режимы» справедливо только для колоды из многих слов;
для одного слова круг вырождается в одну карточку.

Развилка для правки: либо тренировка одного слова выдаёт N карточек этого слова с разными
режимами (по числу применимых), либо кнопка называется честнее.
