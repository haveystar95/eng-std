## Дефекты

### D-1 · Вызовы починки перевода физически не могут попасть в `api_request_logs` — 256 уже потеряны

**Серьёзность: высокая.** Логирование спенда.

`OpenAiTranslationRepairer.php:40` помечает свой вызов `purpose = 'translation_repair'`:

```php
$response = $this->context->run('translation_repair', null, fn () => Http::withToken(...
```

CHECK-констрейнт `api_request_logs_purpose_check` (миграция `2026_08_12_170000`, строка 26)
такого значения не знает:

```
CHECK (purpose IS NULL OR purpose IN ('generation','images','enrichment','realtime','recap','example_regen'))
```

Проверено прямым INSERT в транзакции с откатом:

```
ERROR:  new row for relation "api_request_logs" violates check constraint "api_request_logs_purpose_check"
DETAIL:  Failing row contains (…, translation_repair, null).
```

`EloquentApiLogWriter::write()` ловит `Throwable`, пишет `Log::warning` и возвращает `null`
(«Observability must never break the request it is observing») — **вызов исчезает молча**. Побочно:
`$id === null` → `LogOutboundHttp:72` не делает `context->record($id)`, так что строку нельзя было бы
привязать и к коллекции.

**Это уже произошло, не гипотеза.** В `storage/logs/laravel.log` — **256** предупреждений
`api log write failed` с этим констрейнтом, все с `translation_repair`, между **2026-08-12 18:47:41**
(первый — через 1.5 часа после самой миграции) и **2026-08-13 11:48:00**. Скорее всего это массовый
прогон `repair:content-language` (`RepairContentLanguageHandler:50` дёргает тот же порт): весь его
спенд в логе вызовов отсутствует.

**Что ломается:** `GenerationPipeline::addRepairs()` суммирует токены починок в
`generation_requests.cost_usd`, а `api_request_logs` их не видит — два реестра расходятся ровно на
неудачных прогонах, то есть «дорогая генерация с ретраями» в логе вызовов выглядит дешёвой.
Транзакцию это не рвёт: починка идёт до `tx->run()`, вне транзакции записи.

Данный прогон дефект не задел только потому, что барьер не сработал ни разу.

### D-2 · Ридер выбирает перевод без фильтра по языку и без детерминированного порядка

**Серьёзность: высокая.** Контент, который видит учащийся.

Три ридера — `EloquentTermContentReader:23`, `EloquentTermEnrichmentExportReader:30`,
`EloquentEnrichmentTargetReader:76` — читают одинаково:

```php
DB::table('term_translations')->whereIn('term_id', $ids)->orderByDesc('is_primary')->get()
// $translations[$termId] ??= $row->text;   ← первая строка побеждает
```

Две независимые дыры в одной строке:

1. **Нет `where lang = <язык пользователя>`.** В базе **103** термина `lang='en'` имеют переводы, но
   ни одного `ru` (75 строк `uk`, 44 `de`). Такому термину ru-пользователь получит украинский или
   немецкий текст как **вопрос карточки**. Фолбэка нет — есть просто отсутствие фильтра.
2. **Нет второго ключа сортировки.** `FindOrCreateTermHandler:31` при дедупе добавляет перевод
   безусловно, и `ImportTerm` ставит `isPrimary: true` каждому — **28** терминов в базе несут
   больше одной `is_primary` строки. Порядок среди равных в SQL не определён.

Доказательство п.2 живое: термин `01KZB67VNNTWTPHA2VJXHQ9SH1` («Can I pay by card?») получил в этом
прогоне вторую primary-строку. `GET /api/v1/collections/01KZXWP0BY7BVHZ72FXY0TA75T` вернул
**«Могу я оплатить картой?»** (старая, `01KZET6V9J06DDJ8ZVJC70E1ZW`), а тот же логический запрос в
psql первой отдал **«Могу ли я заплатить картой?»** (новая, `01KZXWP0GKES71A3AHSRF0SK1Q`).

Контраст показателен: строкой ниже, для `term_examples`, порядок закреплён `orderBy('id')` и снабжён
подробным комментарием именно про эту опасность («which one must be PINNED, not whichever the heap
hands back»). У переводов такой защиты нет, хотя ситуация ровно та же.

### D-3 · `ModelCost` не учитывает кэшированные токены — стоимость завышается

**Серьёзность: низкая.** Точность учёта.

`ModelCost::estimate()` (`app/Modules/Shared/Domain/Service/ModelCost.php:58`) считает
`($tokensIn / 1000) * $inRate`, не различая `prompt_tokens_details.cached_tokens`. В этом прогоне
кэш составил **32000 из 36709** входных токенов станка (87 %). При скидке OpenAI 50 % на
кэшированный вход станок стоил **$0.003552**, а посчитан как **$0.005952** — завышение на 68 % по
этапу и на 10 % по прогону. Направление ошибки безопасное (пере-, а не недосчёт), но с ростом
доли кэша расхождение растёт.

### D-4 · Маркер `enrich-v1` не различает версию промпта и валидатора

**Серьёзность: низкая (в этом прогоне не выстрелил).** Прослеживаемость.

`BuildTermEnrichmentsHandler::VERSION = 'enrich-v1'` не менялся ни при вводе `enrich_pack.v2`
(коммит `31af583`, 2026-08-12 23:43), ни при валидаторе v2 (`1f78336`, 23:29). В базе живут только
`enrich-v1` / `enrich-v1-topup` / `enrich-v1-topup2` — по маркеру **нельзя определить**, каким
промптом и каким валидатором сделана конкретная строка, а `pending()` пропускает термин по маркеру.

Здесь обошлось: №10 помечен сегодня в 11:56, то есть уже после обеих правок, — пропуск ничего не
потерял и сэкономил вызов. Но правило «пропускаем по маркеру» опирается на допущение, которое сам
маркер не выражает. Докблок оговаривает бамп как решение человека, так что это осознанный долг, а не
опечатка — фиксирую как риск.

### D-5 · Низкое покрытие span-гейта: `example` дословно повторяет `text`

**Серьёзность: средняя.** Годность контента для `pick_correct`.

Только **3 из 12** терминов набрали ≥2 span-различных дистрактора. Корень — не валидатор: у 6 из 12
терминов `example` **дословно равен** `text` («What do you recommend?» → пример
«What do you recommend?»). У трёх таких (№3, №5, №9) модель вернула `distractors: []` — в строке,
которая и есть сам термин, ломать нечего, не задев ответ.

Промпт v6 требует «one short, natural **sentence that uses** `text`», но для items типа `phrase`,
которые сами являются законченными предложениями, модель возвращает их же. Тема с уклоном во фразы
(а v6 сам просит 60–70 % многословных) систематически лишает станок материала.

### D-6 · Дистрактор отличается от эталона типографским апострофом

**Серьёзность: очень низкая.** Косметика контента.

Термин №2 «to go»: эталон-пример `I'd like an espresso to go.` (прямой апостроф `'`), записанный
дистрактор `I’d like an espresso to gone.` (**типографский** `’`). Валидатор пропустил законно —
`LexicalNormalizer::canonicalize()` срезает пунктуацию, — но в упражнении «выбери верное» неверный
вариант отличается от эталона ещё и невидимым символом помимо грамматической ошибки.

### Замечание по инструментам (не дефект кода)

`enrich:audit-distractors` не имеет опции `--collection` — аудит только глобальный. Требование
наряда «сухой аудит по коллекции» выполнено более сильным способом (0/0 по всей базе, 1006 строк),
но адресно прогнать его нельзя.
