## 1. Пара «реплика роли ↔ твой ход» — ПОЧИНЕНО

**Как выглядело.** День 3, знакомство с репликами. Над сборкой ВОПРОСА «How is ownership split
across the team?» стояла ситуация «Тех лид хочет понять, что именно ты делал в прошлых проектах» и
реплика роли «What were you personally responsible for?». Человеку предложили собрать вопрос в ответ
на вопрос.

**Причина.** Данные были правильные — цепочка дня однозначна:

```
role  pair=ask   s3.2  Do you have any questions for me?
you   pair=ask   s3.2  How is ownership split across the team?
```

Цепочку не читал `SituationalPrompt`: он искал пару по `skill_ref` и при нескольких кандидатах брал
наименьший term id. У умения `s3.2` в этом дне ДВЕ реплики роли, и тай-брейк выбрал не ту.
Тай-брейк был честной попыткой выбрать хоть что-то, пока выбирать было нечем: цепочки (P2 v0.5)
тогда ещё не существовало.

**Починка.** Пара берётся из цепочки — ближайшая реплика роли выше по ней. Подбор по `skill_ref`
остался ЗАПАСНЫМ путём для дней, написанных до цепочки, и для хода, которого в цепочке нет (карточка
чужого дня в шве). Обратная совместимость канона §9 сохранена. Тип обмена (`pair`) намеренно не
спрашивается: ближайшая реплика роли выше по цепочке И ЕСТЬ пара, чем бы обмен ни был.

Решение **303**; отменённый тай-брейк — в разделе «Отменено». Замок: «pairs a move with the line
said right before it, not with another line of the same ability» — проверено, что без правки
краснеет.

**Хвост, который остался у людей на телефонах.** Присест хранится на устройстве ЦЕЛИКОМ, вместе с
пейлоадом, который сервер уже прислал (`PlanSittingStore`), и возобновление его переигрывает.
Починка видна только на СВЕЖЕЙ посадке: «Позже» на шве присестов или конец дня.

## 2. «6months» ≠ «six months» — верная реплика получает «Не то»

**Как выглядело.** «Скажи сам», реплика «Great, I need it for six months.» Сказано верно, распознано
как «Great, I need of 6months.» Вердикт — «Не то», и подчёркнуто **«months.»** — единственное слово,
которое человек как раз произнёс.

**Воспроизведено на сервере:**

```
heard  «Great, I need of 6months.»  →  great i need of 6months
credit = wrong   coverage = 0.429   rule = key_and_rest
missing = it, for, six, months
```

**Причина — две независимые вещи, обе про то, КАК ПИШЕТ распознаватель:**

1. **число словом против цифры**: карточка говорит `six`, распознаватель пишет `6`;
2. **склейка**: `6months` пришло одним токеном.

Пере-нарезка границ (`SpokenWordBoundary` / клиентский `_alignBoundaries`) существует ровно для
второго и разложить `6months` не смогла: она сверяется со словами ЦЕЛИ, а там `six`, а не `6`. Одна
беда закрыла другую.

Проект про это уже знает и знает наполовину: докблок `SpokenCoverage::consume` прямо говорит, что
транскрипт содержит «5» там, где реплика говорит «five» — но там чинили `TypeError` от
`array_count_values`, а не сравнение.

**Предложение.** Нормализация речи (`SpeechNormalization`, версия 1 → 2, она же на проводе и в
клиентском зеркале) получает шаг числительных: расклейка цифра↔буква, затем цифра → слово. Это
ровно та же природа, что и таблица аббревиатур («sequel» → SQL): не ошибка человека, а то, как
пишет машина. Расклейку правильно вести ПРОТИВ СЛОВ ЦЕЛИ — тем же принципом, что и `SpokenWordBoundary`
(«ничто здесь не может выдумать слово, которого карточка не просила»).

Ожидаемый вердикт после правки для этого случая: ключ `months` найден, остальные слова реплики
покрыты на 4/6 = 0.67 ≥ 0.6 → **верно**.

Это внутри полномочий наряда SPEECH-2 («грейдер речи: speaking_keys, нормализация»).

## 3. Экран пройденного дня зовёт в никуда

**Как выглядело.** День 1 пройден целиком, день 2 не собрался (`failed`). На экране дня — «Повторить
ошибки» и «Продолжить». Обе ведут в тупик; вторая — через 35 секунд белого экрана (см. п. 4), потом
«Здесь сейчас нечего проходить — этот этап уже закрыт».

**Сервер отвечает честно:**

```
POST /api/v1/plans/01M20WFC…/days/1/session   {"session_id": "01M20XC2CZ…"}
409  plan_sitting_empty
     "Для дня 1 плана 01M20WFC… нечего собрать."
```

**Причина.** Экран дня не предвидит пустой посадки: он рисует «Продолжить» всегда, а знание о том,
что собирать нечего, есть только у сервера и приезжает уже ошибкой. Та же болезнь, что чинили в
DAY-GATE-1 («итог присеста зовёт в следующий день, пока текущий не пройден»), с другой стороны: день
пройден, следующий не собрался, а кнопка всё равно зовёт.

**Что делает правильно вкладка «План»** — и это доказывает, что данных на пейлоаде хватает: она
показывает «День 2 · сцена 2 · **не собрался**», причину словами («Сорвалась сборка реплик») и
рабочую кнопку «Собрать заново».

**Предложение.** Экран дня читает то же, что вкладка. Кнопка пройденного дня, за которым нет
следующего, либо не рисуется, либо ведёт туда же, куда ведёт вкладка. Пустая посадка — предвиденное
состояние, а не ошибка транспорта.

## 4. Тридцать пять секунд белого экрана: ретрай 409

**Факт из журнала** — девять одинаковых запросов с ОДНИМ `session_id` (то есть одно нажатие, а не
девять):

```
16:24:44  409   16:24:44  409   16:24:45  409   16:24:47  409   16:24:51  409
16:24:58  409   16:25:05  409   16:25:12  409   16:25:19  409
```

Интервалы 0, 1, 2, 4, 7, 7, 7, 7 секунд.

**Причина — найдена в коде.** Riverpod 3 ретраит УПАВШИЙ ПРОВАЙДЕР сам:

```dart
// riverpod-3.3.2/lib/src/core/provider_container.dart:940
static Duration? defaultRetry(int retryCount, Object error, {
  int maxRetries = 10,
  Duration maxDelay = const Duration(milliseconds: 6400),
  Duration minDelay = const Duration(milliseconds: 200),
}) {
  if (retryCount >= maxRetries) return null;
  if (error is ProviderException || error is Error) return null;
  ...
}
```

`DioException` — ни `ProviderException`, ни `Error`, поэтому ретраится. Десять попыток,
200 мс → 6.4 с — ровно наблюдаемая картина. Пока они идут, экран показывает `loading`.

409 — это ОТВЕТ, а не сбой связи: он не изменится от повторения. Ретраить его нельзя ни разу, тем
более десять.

**Предложение.** `planSessionProvider` (и всё, что ходит в API) получает `retry`, возвращающий
`null` для окончательного доменного ответа: 4xx с RFC 7807 `code`. Половина этого знания в клиенте
уже есть — `problemCode(e)` и `isPermanentReject(e)` в `api_client.dart`; последняя знает только
422/413 и живёт для очереди ревью.

## 5. Гейт `translation_missing_key` не умеет вид глагола

**Как выглядело.** День 2 плана `01M20WFC…` не собрался. Последний, добивший его отказ:

```
card.translation_missing_key [Then this won't suit me.]:
перевод реплики не содержит перевода ключевой карточки «suit» («подходить») —
ученик читает вопрос, в котором не спрошено то, что карточка требует произнести
```

**Механизм.** `TranslationKeyPresence` сравнивает не подстроки, а 5-буквенные ОСНОВЫ — специально,
чтобы падежи не мешали. Ключ «подходить» → основа **«подхо»**. Проверено на живом классе:

```
ОТКАЗ   — Тогда мне это не подойдёт.
ОТКАЗ   — Тогда это мне не подойдет.
ПРОШЛО  — Тогда мне это не подходит.
ПРОШЛО  — Тогда такой вариант мне не подходит.
```

Дело в ВИДЕ глагола: «подходить» → совершенный «подойдёт», и корень меняется
(**подхо**дить / **подой**дёт). Префиксное сравнение рассчитано на окончания и чередование в корне
перепрыгнуть не может.

**Это повтор истории.** Докблок самого класса описывает ту же болезнь в прошлой форме: ключ «quiet»
→ «тихий», корень три буквы, пятибуквенная основа съедала слово целиком — «модель написала
правильный русский четыре раза, и гейт четыре раза его отказал: $0.17 живых денег в одну
арифметическую ошибку». Тогда починили ДЛИНУ основы. Сейчас причина другая — смена корня, — а цена
та же.

**Предложение.** Сравнивать не «префикс фиксированной длины», а фактическое общее начало с полом в
3 буквы: «подхо»/«подой» дали бы 4 общих буквы и прошли. Класс сам объявляет, в какую сторону
ошибаться: «гейт, отказывающий хорошему дню, стоит дороже, чем гейт, пропускающий слабую строку».

**Чего доказать нельзя.** Какой именно русский написала модель — см. п. 6.

## 6. `raw_response` не пишется для плановых вызовов

Разбор п. 5 упирается в стену: в `generation_requests` у плановых вызовов `raw_response` пуст
(`strlen = 0`); он пишется только для генерации коллекций. В журнале остаются английская реплика и
имя ключа из текста нарушения — и всё.

То есть на вопрос «что именно модель написала и почему это отказали» ответить нечем, а именно этот
вопрос задают каждый раз, когда день сгорает за деньги.

**Предложение.** Писать ответ модели для плановых вызовов так же, как для коллекций. Одна строка в
адаптере; хранение — уже существующая колонка.

## 7. Сцена спорит с гейтами

**Полная история дня 2** (сцена «Осмотр квартиры»):

```
s2.1  спросить, что входит в арендную плату
s2.2  уточнить правила по домашним животным
s2.3  спросить о минимальном сроке аренды        ← вот это

реплики роли из каркаса:
  The rent includes water, but electricity is separate.
  It's fully furnished.
  The minimum term is six months.
  I'm afraid pets are not allowed in this flat.
  Do you have any questions about the bills or the contract?
```

**Заход 1** — 16:23:19, $0.0435:

```
day.pairs_too_few:     в сцене осталось 3 обмена — меньше 4
card.clone:            [The minimum term is six months.] две карточки собираются в один текст
card.chunk_is_basic:   [four months] связка целиком собрана из базовых слов
card.chunk_is_basic:   [six months]  — то же
```

**Заход 2** — 16:23:56, $0.0430:

```
card.clone:                   [The minimum term is six months.]  — снова
card.translation_missing_key: [Then this won't suit me.]         — см. п. 5
```

**Починка** — 16:23:58, $0.0123: вызов прошёл и вернул карточки по адресу, день пересобрался и всё
равно не прошёл. Выжившее нарушение — одно: `say[3].translation`. Попытки исчерпаны → `failed`.

**Столкновение.** Умение `s2.3` — «спросить о минимальном сроке аренды», реплика каркаса — «The
minimum term is six months». А `card.chunk_is_basic` запрещает связку, собранную только из базовых
слов: числа базовые, «months» тоже (в дне 1 он получил прямым текстом `card.word_is_basic [months]`
— «числа живут на полке numbers»). **То, ради чего сцена написана, гейты писать не дают.** Модель
дважды упёрлась в это и дважды слепила одну и ту же реплику каркаса в две карточки (`card.clone`).

Это вопрос не к коду, а к канону: либо сцена про сроки не должна ставиться, либо числа перестают
быть базовыми внутри связки, которая их и учит.

**Деньги.** День 2 — 27 вызовов, **$0.1723**:

| вызов | раз | $ |
|---|---|---|
| `plan_pair_judge.v0.2` | 17 | 0.0518 |
| `plan_pair_rewrite.v0.2` | 7 | 0.0217 |
| `plan_day.v0.8` | 2 | 0.0865 |
| `plan_day_repair.v0.3` | 1 | 0.0123 |

Весь план за день — 41 вызов, **$0.2843**.

**Выход, который работает.** «Собрать заново» на вкладке «План»: `PlanDay::reopenForRetry()` ставит
статус `pending` и возвращает счётчик на `MAX_ATTEMPTS − 1`, то есть даёт дню ещё одну попытку.
Проверено по коду; кнопка проходит даже при исчерпанных двух попытках.
