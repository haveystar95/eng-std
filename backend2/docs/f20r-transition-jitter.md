# F20-r — «лаги тренажёра»: разбор, причина, правки

Статус: **закрыто.** Причина найдена и исправлена, гейты зелёные, изменения приняты.

Документ служит двум целям: зафиксировать причину и **быть регресс-инструкцией** — если ощущение
«тренажёр подтормаживает» вернётся, начинать надо с раздела «Методика», а не с гипотез.

---

## 1. Симптом

Подлагивания в тренажёре: рывки на переходах между карточками, залипание нажатий (фишки
word_bank подставляются не сразу, варианты ответа реагируют через полсекунды), задержка появления
карточки подсказки, обрезанное начало первого произнесённого слова. Проявлялось «часто, но не
всегда», сильнее во втором проходе подряд.

Наблюдалось на iPhone 13 Pro (iOS 27 beta, 120 Гц). На iPhone 13 (iOS 26.4.1, 60 Гц) те же провалы
присутствовали, но при бюджете кадра 16.7 мс вместо 8.3 стоили вчетверо меньше пропущенных кадров и
замечались реже.

---

## 2. Причина

Пакет `flutter_tts` 4.2.5, `ios/Classes/SwiftFlutterTtsPlugin.swift`:

```swift
private func shouldDeactivateAndNotifyOthers(_ session: AVAudioSession) -> Bool {
  var options: AVAudioSession.CategoryOptions = .duckOthers   // ← ровно то, что ставим мы
  if #available(iOS 9.0, *) { options.insert(.interruptSpokenAudioAndMixWithOthers) }
  options.remove(.mixWithOthers)
  return !options.isDisjoint(with: session.categoryOptions)
}

// speechSynthesizer(_:didFinish:) — после КАЖДОЙ произнесённой фразы
if shouldDeactivateAndNotifyOthers(audioSession) && self.autoStopSharedSession {
  try audioSession.setActive(false, options: .notifyOthersOnDeactivation)
}
```

`autoStopSharedSession` по умолчанию `true`. `duckOthers` мы выставили в device-batch F10, чтобы
озвучка звучала через аппаратный беззвучный режим. В результате **после каждого слова** выполнялся
блокирующий системный демонтаж аудиосессии с уведомлением остальных приложений.

Это объясняло весь набор симптомов сразу:

- замирания ~600 мс, по одному на произнесённое слово;
- «не всегда» — тап или кадр страдал, только если попадал в чужое окно;
- обрезанное начало первого слова — сессию гасят, следующая фраза стартует, пока она поднимается;
- триаж гладкий — там нет TTS.

### Правка

`Pronouncer.warmUp()` — при старте тренировки: `autoStopSharedSession(false)` +
`setSharedInstance(true)` + категория + язык + скорость + прогрев синтезатора одной фразой на
нулевой громкости (холодный старт голоса съедал начало первого слова).

`Pronouncer.release()` — при уходе с экрана: `autoStopSharedSession(true)` (вернуть плагину его
поведение по умолчанию) + `setSharedInstance(false)`.

**Порядок в `release()` важен.** `autoStopSharedSession` живёт на нативном синглтоне плагина, а
`Pronouncer` создаётся ещё и в `collection_detail_screen.dart`, у которого нет своего жизненного
цикла аудио. Оставить флаг в `false` — значит, что кнопка «озвучить» на экране коллекции оставит
сессию активной с `duckOthers` бессрочно. Удержание сессии — поведение **только экрана тренировки**.
Это же гарантирует, что realtime-диалог, поднимающий свою `playAndRecord`-сессию, никогда не
встретит удерживаемую нами.

## 3. Методика — что мерить при рецидиве

Инструментирование ставилось и снималось шесть раз. Полезными оказались **три** сигнала; они
оставлены в приложении и выключены по умолчанию.

**Где тумблер:** Профиль → Разработка → **Perf monitor** → переключатель «Record stalls, slow frames
and slow taps». Там же «Copy to clipboard» и дамп в файл `perf.txt` в documents-каталоге.
Код: `mobile/lib/data/perf_log.dart`, экран `mobile/lib/features/profile/perf_log_screen.dart`.
Раздел виден только при `DEV_MENU`.

| Сигнал | Что даёт |
|---|---|
| **Пульс изолята** — таймер 100 мс, докладывающий, насколько поздно сработал | Кадровые метрики говорят «поток не взял кадр». Пульс говорит «Dart-изолят не выполнялся». Это разные вещи, и второе не видно ничем другим. |
| **Метка экрана** (`@session` / `@triage` / `@app`) | Даёт контрольный опыт. Триаж не имеет ни TTS, ни клавиатуры: «гладко там, рвано в тренажёре» локализует причину за один прогон. Именно это и нашло F20-r, сняв разом версии про бету iOS, ProMotion, память и сборку мусора. |
| **Задержка нажатия** (тап → обработчик) | Жалоба «кнопки не реагируют» невидима для кадровых метрик: кадры в порядке, ждёт само касание. |

Порядок прогона при рецидиве: **сначала триаж 60–90 секунд, потом тренажёр**, и сравнить строки
`! isolate stalled` по метке экрана. Если стоят обе — причина глобальная. Если только `@session` —
причина внутри тренажёра.

Важно: приложение ставится **релизным** билдом (в debug оно не стартует без разрешения Local
Network), поэтому консоли нет — всё читается с экрана монитора.

## 4. Ложные следы — не повторять

Все проверены измерением и **исключены**:

| Версия | Чем опровергнута |
|---|---|
| Веер перезапуска drift-стримов; `termProgressForProvider` без `autoDispose` | Обычный сеанс, где ответы реально двигают прогресс: глобальные стримы не эмитили ни разу после старта. drift не эмитит при неизменных данных, а сама БД живёт в фоновом изоляте. Провайдеры копятся и не стоят ничего. |
| Потолок `imageCache` / давление памяти / сборка мусора | В триаже кэш был те же 97.6 МБ при потолке 100 — и триаж гладкий. Одинаковое давление, разный результат. Пробовал лимит 40 МБ — стало хуже (LRU вытесняет прогретую следующую карточку), откачено. |
| Адаптивная частота ProMotion | Колонка `vsync` показывала ровно 8.3 мс на каждом переходе — дисплей всю сессию шёл на честных 120 Гц. |
| iOS 27 beta | Те же ~600 мс замирания на iPhone 13 с релизной iOS 26.4.1. |
| Объём данных аккаунта («нагруженный против свежего») | У второго телефона данных больше (127 терминов против 102), веер стримов вдвое шире — лагов меньше. |
| «Анимация стартует поздно» | Замер тап → первый кадр: 1–9 мс на каждом переходе. |
| Двойной декод из-за несовпадения `cacheWidth` | `Image.network(cacheWidth:)` идёт через `ResizeImage.resizeIfNeeded` и даёт тот же ключ кэша, что `precacheSessionImage`. Ключи совпадают. |

Отдельный урок: **пульс изолята сам по себе завышает картину.** Из ~18 замираний в одном прогоне у
15 стоял `busy -` и ни одно из них пользователь не заметил — это сон простаивающего цикла событий
на статичном экране. Судить надо по совпадению замирания с анимацией или нажатием, а не по факту.

## 5. Прочие правки, сделанные попутно

### Клиент

**Баннер карточки** (`session/session_exercise.dart`). Было: серая плашка → пустота цвета бумаги →
проявление 180 мс; при отсутствии фото блок схлопывался и текст подпрыгивал на 164 px. Стало:
плашка **под** картинкой, высота известна с первого кадра (оболочка передаёт `photoUrl` /
`photoResolved`), кэшированная картинка показывается мгновенно, холодная ждёт конца слайда.

**Прогрев фото** (`session_screen.dart`). Было 40 обращений и декодов на 20 карточек — каждая
грелась дважды, и грелись все режимы. Стало: один резолв на карточку, декод только для
`multiple_choice` (единственный режим с баннером), фото для фидбека неверного ответа греется
точечно. **40 → 3–7 за сессию.**

**Освобождение картинок.** При переходе на карточку N освобождается фото N−3. Кэш перестал копиться
через проходы: 37–45 МБ вместо подъёма к 84–95 при потолке 100.

**Озвучка listening:** задержка 250 → 100 мс. Полная задержка была частью F20 (вызов TTS стопорил
слайд), но на карточке аудирования четверть секунды тишины читается как зависание.

### Батч и синк (см. отдельный раздел 6)

### Бэкенд

`CachedLatencyMedianReader` клал в кэш сериализованный доменный объект `LatencyBaseline`. Строка
пережила свой класс, развернулась в `__PHP_Incomplete_Class`, проверка типа возврата упала — и
**каждый `POST /reviews/batch` отвечал 500** в течение суток (TTL 86400). Клиент справедливо считал
500 транзиентной ошибкой, поэтому очередь ответов не чистилась и росла через сессии.

Стало: в кэше хранится `int`, а всё, что не `int`, считается отравой — ключ сбрасывается и значение
пересчитывается на первом чтении, а не через сутки.

## 6. Батч и синк — изменение поведения

Было: `record()` заканчивался безусловным `unawaited(flush())`, поэтому «батч» всегда состоял из
одного ответа, а успешная выгрузка безусловно запускала `SyncService.sync()` (который внутри тянет
ещё и `GET /stats`). **Три запроса на каждый ответ, 60 за практиковую сессию из 20 карточек.**

Стало, две правки:

1. **Синк только если что-то планировалось.** Флаг `scheduledAny` поднимается, только если в
   успешно выгруженном чанке был непрактиковый ответ. Практика по инварианту не двигает прогресс
   (`SubmitReviewsHandler::foldIntoProgress` отфильтровывает `isPractice`), поэтому дельта после
   практики физически не может ничего вернуть — измерено: ноль строк, ни разу.
2. **Практика выгружается одним батчем в конце.** `if (!isPractice) unawaited(flush());` — ответ
   ложится в durable-очередь, вся пачка уходит одним `POST /reviews/batch` на экране итогов.

**Один запрос на сессию вместо шестидесяти.** Обычный (планирующий) сеанс не тронут: там выгрузка и
синк по-прежнему на каждый ответ, потому что строка «увидишь снова через N дней» ждёт расписания.

Сохранено: порядок (`client_seq` присваивается в `record()`, чанки шлются по порядку, сервер
сворачивает по нему), durability (`await _queue.save()` до возврата из `record()`), идемпотентность
(клиентский ULID). Триггеры выгрузки: старт приложения, возврат сети, возврат из фона, экран итогов,
любой планирующий ответ.

Осознанно принятая разница в поведении:

- практиковые ответы доезжают до сервера позже (конец сессии, а не по одному);
- во время практики локальное зеркало не обновляется — чужие изменения приедут на следующем
  триггере;
- очередь растёт внутри сессии до 20 записей, а `ReviewQueue.save()` переписывает весь блоб в
  Keychain на каждый ответ → **это адресуется отдельной задачей F20-r2** (перенос очереди в drift,
  потолок очереди, экспоненциальный backoff).

---

## 7. Что осталось

- **F20-r2** — очередь ревью из Keychain в drift, потолок очереди, backoff на транзиентных ошибках.
- Экран итогов строится 47–59 мс (двадцать строк + `IntrinsicHeight`).
- `termProgressForProvider` без `autoDispose` — измерено как безвредное, но за два прохода копится
  40 живых подписок.
