# Реестр промптов — всё, что тратит деньги на модель

**Правило.** Ни один промпт не появляется в коде без строки в этой таблице. Новый промпт, новая
версия существующего, новый вызывающий — сначала строка здесь, потом код. Строка без промпта
(промпт удалён, адаптер выпилен) убирается тем же коммитом, что и код.

Это НЕ инвентарь файлов — файлы видно `ls`. Это ответ на вопросы, которых в коде не видно: **кто
платит, за что, сколько это стоит и что проверяет ответ**. Реестр читается перед тем, как заводить
ещё один вызов модели: половина строк ниже — уже существующий ответ на задачу, которую хочется
решить новым промптом.

Границы: сюда попадает всё, что **отправляет текст в языковую модель и платит по токенам**.
Не-модельные внешние API (Pexels, DeepL) — в отдельной таблице внизу, потому что путать их с
промптами дороже, чем перечислить.

Версии и модели ниже — **дефолты кода на 2026-09-17** (после наряда GEN-3 и его доработки); живое значение всегда в `config/services.php`,
`config/plan.php` и `.env`. Цена — ориентир за один вызов при типичном входе, по `ModelCost` (`Shared/Domain/Service`).

## Учёт трат плана

Плановые вызовы не пишут в `generation_requests`: цена, задержка, число попыток, версия промпта и
**версия сборки сервера** лежат на самой строке — `plans.cost_usd_plan` / `latency_ms_plan` /
`attempts_plan` / `prompt_version_plan` / `build_version` и `plan_scenes.cost_usd_lesson` /
`latency_ms_lesson` / `attempts_lesson` / `prompt_version_lesson` / `build_version`. Цена — сумма
всех попыток (отбитая попытка тоже оплачена). Попыток у обоих вызовов не больше двух: ретрай
покупается только невалидным JSON/схемой или проверкой в режиме `gate`; вторая неудача = `failed`,
третий вызов покупает только явный запрос клиента (`…/build/retry`, `…/lesson/retry`). Лог вызовов
помечает их `purpose = 'plan'` (`api_request_logs`) — это лог, а не реестр.

**Журнал вызовов модели** (`model_calls`, модуль Observability, наряд GEN-3) — бухгалтерия денег, которые ушли вендору, в том числе
тех, за которые ответа нет. Каждый вызов адаптеров `ContentModelPort` (OpenAI, Anthropic, Gemini) и песочницы пишется **до** вызова
(`started`: вендор, модель, назначение = `purpose` лога, оценка входных токенов — байты тела / 4, сколько ждём ответа) и
дополняется после: `completed` (`tokens_in`, `cached_tokens`, `tokens_out`, `cost_usd` по `ModelCost` со скидкой кэша, задержка),
`failed` (вендор ответил статусом ошибки) или `lost` (ответа нет — наш таймаут или обрыв: модель могла досчитать, и вендор
списал). Строка `started`, пережившая своё ожидание больше чем на минуту (процесс умер на вызове), становится `lost` командой
`model-calls:sweep-lost` (планировщик, раз в 10 минут). Запись в журнал никогда не роняет вызов (ошибка — в лог приложения).
Прямые адаптеры первой генерации (`OpenAiWordLookup`, `OpenAiCollectionGenerator`, `OpenAiTermEnricher`,
`OpenAiEnrichmentPacker`, `OpenAiExampleRegenerator`, `OpenAiTermTransliterator`, `OpenAiTranslationRepairer`,
`OpenAiDialogSummarizer`) и минтеры realtime в журнал пока не пишут — только в лог запросов.

Счётчики проверок — `plan_check_counters` по версии промпта (у урока — коды валидатора: `counted` — каждая находка,
`gated` — фатальная, задержавшая день, `failed` — оставшаяся при `failed`; не находки — `lang.pack_missing` — проверка не
запускалась, у языка пары нет пакета, по разу на код, и `judge.unavailable` — судья швов не ответил); находки каждого
ответа — `checks_json` на плане/сцене. Починка P2R и судья швов дописывают свою цену (и время) в
`plan_scenes.cost_usd_lesson` / `latency_ms_lesson` (попыток не прибавляют): в сборке — всегда, командой — только при
`--apply`; без него — только лог запросов. Админка: `GET /admin/api/plans/checks`; строка `plan` в
`GET /admin/api/costs` — сумма двух колонок выше.

**Судья окна** (`slot_judge.v3`, наряд SESSION-1a; v3 — CONV-2) в счёт сцены и плана не попадает ВОВСЕ: он судит попытку
ученика, а не урок, и `cost_usd_lesson` / `latency_ms_lesson` не трогает. Цена, токены и задержка его вызова
лежат только в **логе исходящих** (`purpose = 'plan'`, `api_request_logs`, строка `plan.slot_judge` в логе
приложения) и на самой карточке — `day_cards.response.judge` (`model`, `prompt_version`, `cost_usd`,
`latency_ms`, `tokens_in`, `tokens_out`; заполнены, только когда судила модель). Счётчик у него один:
`judge.unavailable` в `plan_check_counters` по версии `slot_judge.v3`, action `counted` — `+1` на каждый
вердикт, который должна была дать модель, а дал код (кап исчерпан, молчание, ответ не по форме). Отказ по
покрытию («каркас не прозвучал») и зачёт по известному наполнению модель не зовут и счётчик не трогают, так что
`judge.unavailable` — это счётчик молчания вендора, а не счётчик ошибок ученика.

## Как читать колонки

- **версия** — то, чем стамповано содержимое (`prompt_version` на строке контента). Бамп версии
  промахивается мимо кэша промпта и заставляет перегенерацию — это его вторая работа.
- **валидатор** — **детерминированный** код, который судит ответ. «нет» в этой колонке значит, что
  ответ принимается на слово; это допустимо (RECAP — текст для человека), но должно быть видно.
- **цена ≈** — один вызов при типичном входе. Умножать на число терминов/дней самому: план на 5 дней —
  это PLAN + 3×LESSON ≈ **$0.2–0.35** (три дня-сцены; повторение и репетиция модель не зовут).

## Что реестр НЕ отвечает

Какая версия сейчас в бою на проде — это `.env`. Какие секции входят в составную версию — это
`PromptLibrary::COMPOSED`. Почему промпт устроен так — это сам файл промпта и отчёт наряда,
который его написал (`docs/research/`, `docs/bakeoff-*`).
